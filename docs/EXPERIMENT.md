# 首轮验证计划

状态：计划，尚未执行。没有用户访谈、真实使用统计或销售数据。不自动向任何人发送消息或发帖。

## 第一轮：任务能否完成

目标：由项目拥有者邀请 5 位会导出 HAR 的开发、测试或技术支持人员，自愿试用。

任务：导入获授权的日志，定位异常请求，清理仍敏感的路径信息，然后导出能交给同事的材料。用户文件不发送给维护者。

记录：完成耗时、是否需要指导、遗漏的敏感信息类型（不记录原始值）、报告哪里无用，以及现有工具是否更好。

继续标准：至少 3 人能够独立完成，并能说出一个比原流程便利的具体环节。此标准是内部决策门槛，不是行业基准。

## 第二轮：有没有重复需求

目标：在获得分享许可后，由拥有者发布一次虚构样本的演示，收集自愿反馈。发布 GitHub、社区和演示站点都需拥有者确认后执行。

不使用追踪脚本。用户自愿填写匿名反馈表，或在公开仓库提交不含真实日志的问题。

建议问题：

1. 最近两周是否再次使用？
2. 原流程是什么，为什么还会选用这个工具？
3. 最想补充的一个功能是什么？
4. 如果这个工具消失，会怎样完成同一任务？

如果 20 位目标用户中没有人再次使用，先查任务频率与替代方案，不直接堆功能。

## 第三轮：付费验证

仅在重复使用出现后，向有明确需求的人展示可交付的新增能力：批量文件、两次 HAR 对比、报告模板或团队内部部署支持。

不把整个基础工具都设成付费，也不提前搭建账号／支付平台。对一次性授权或服务范围先给具体报价，记录对方是否愿意实际支付；口头赞同不算。

当前基础版 MIT 开源准备。任何未来商业功能必须重新评估其交付成本、许可和维护责任。这里不承诺收入。
